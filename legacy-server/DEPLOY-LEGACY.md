# 公网部署与数据保管

## 目前是什么

随行是浏览器访问的网站，也包含 Node.js 服务端和 SQLite 数据库。浏览器保存成员身份凭据，旅行、酒店、分类和勾选记录写入服务器的 `trips.sqlite`。关闭网页不会删除这些记录；清除浏览器数据可能导致身份丢失，需要创建者协助恢复。

目前服务器就是你的电脑。`localhost` 仅本机可用，局域网地址仅同一网络内可访问。电脑关机、休眠或服务停止，同行人就无法访问，但这不等于数据库内容被删除。

## GitHub 可以做什么

仓库 `https://github.com/wenhuawen2-art/1452ooo` 可以保存代码，并作为部署平台拉取代码的来源。GitHub Pages 只提供静态网页托管，不能直接运行本项目的 Node 服务端和 SQLite 共享数据库。

上传时只上传源码、测试和配置。不要上传 `data/`、`backups/`、`.env`、浏览器测试记录或任何 `.sqlite` 文件；这些文件可能含成员访问凭据和旅行隐私。仓库即使公开，也不应该公开数据。

## 推荐：GitHub 代码仓库 + Render Web Service + 持久化磁盘

这是维持现有结构、操作较少的一条部署路径。Render 的持久化磁盘需要付费服务；免费服务的临时文件系统不能用来可靠保存本项目的 SQLite 数据。实际费用以创建服务时的平台报价为准。本仓库中的 `render.yaml` 只是配置模板，不会自动开通或扣费。

1. 将源码提交到你的 GitHub 仓库。
2. 在 Render 登录并连接 GitHub，选择这个仓库创建 Blueprint，读取 `render.yaml`。也可以手动新建 Web Service，填写下表。
3. 检查托管与磁盘费用，再创建服务。
4. 部署成功后打开平台提供的 HTTPS 地址，创建旅行，再把网页内生成的私密邀请链接发给同行人。

| 配置 | 值 |
| --- | --- |
| Runtime | Node |
| Node 版本 | 22.21.1 |
| Build command | `npm install --omit=dev` |
| Start command | `npm start` |
| Health check | `/api/health` |
| 持久化磁盘挂载目录 | `/var/data` |
| 环境变量 `DATA_DIR` | `/var/data` |
| 服务实例数 | 1 |

不要把“静态站点”当作部署类型，也不要漏掉磁盘。使用默认端口环境变量 `PORT` 即可。多人通过同一 HTTPS 地址操作，数据由同一数据库保存，约每 4 秒同步。

如果主要在中国大陆使用，出发前应让每位同行人用自己的移动网络试用。第三方境外托管的实际访问质量取决于网络情况，本项目没有做实地连通性保证。已有云服务器时也可直接部署同一 Node 服务，使用持久化磁盘及 HTTPS 反向代理，并保留 Host 请求头；无需改成纯静态网站。

## 怎样避免丢失

- **持久化磁盘**：正常应用重启和代码更新不会重置该目录；不要主动删除服务磁盘。
- **每日备份**：服务启动时及每小时检查一次，当天没有备份时生成一个 SQLite 一致性快照到 `DATA_DIR/backups/`，并校验可读性。服务停机期间不会生成备份。
- **升级前备份**：首次升级旧分类结构时，自动生成 `before-v2-时间戳.sqlite`，再用事务迁移数据。
- **手动备份**：本地运行 `npm.cmd run backup`；Linux / Render Shell 执行 `npm run backup`。`BACKUP_DIR` 可指定其他备份目录。
- **异地副本**：定期把备份下载到电脑或另一处安全存储。同盘备份不能抵御磁盘删除、主机或账号丢失，不能据此承诺数据永不丢失。备份默认不自动清理，需定期检查磁盘空间。

不要在数据库正在写入时只复制 `trips.sqlite` 原文件，因为 WAL 模式下近期修改可能还在旁边的日志文件里；使用上述备份命令生成独立、完整的快照。

## 迁移当前电脑上的旅行到公网

1. 暂停其他编辑。创建者先在本地为自己生成一次性身份恢复链接并妥善保存，再执行 `npm.cmd run backup`，记录生成的 `.sqlite` 快照；这样恢复链接才会包含在备份中。
2. 在公网服务停止的状态下，将快照通过托管平台支持的安全文件传输方式上传为持久化目录的 `trips.sqlite`。不要通过公开 GitHub 仓库传输。
3. 如果目标已有数据库，先备份旧目标，停止其服务，再替换数据库，并移走目标旧的 `trips.sqlite-wal` / `trips.sqlite-shm` 文件，避免混用两套数据库。
4. 启动服务，检查旅行、酒店、清单和分类。只有从备份时间点以前的内容会被迁移，之后继续编辑的本地内容不会自动合并。
5. 本地地址和公网地址是不同的浏览器来源，身份不会自动转移。创建者把步骤 1 保存的链接中的 `#recover=...` 部分复制到新的 HTTPS 域名后打开，须在 24 小时有效期内使用。其他成员可由已经恢复的创建者协助恢复。单纯重新加入会新建成员，不会继承原个人勾选。

若只是测试数据，最简单的是上线后创建一趟全新旅行，不迁移本地数据库。

## 删除和备份的关系

创建者可以删除当前或已归档旅行。先确认删除范围，再输入旅行名称确认；取消任一步都不会删除。删除后所有同行人和旧邀请都无法访问这趟旅行。历史备份可能仍保留删除前的数据，不会自动恢复到页面中；需要彻底清除时还应处理相关备份。
